# Durable audit export

[简体中文](README.zh-CN.md)

This independent scheduled Worker copies allowlisted audit records through the existing Management API into its own D1 archive. It reuses the [management client](../management-worker/src/client.ts), requests only `management:audit:read`, obtains a short-lived token per invocation and exposes no HTTP trigger or archive-reading route. The earlier management example remains a bounded latest-page poll; this example adds durable continuation and deduplication.

Create a dedicated machine application/role with only the audit-read permission. Configure `AUTH_ISSUER` and `MACHINE_CLIENT_ID`, copy `.dev.vars.example` to `.dev.vars` and fill `MACHINE_CLIENT_SECRET`. Apply the local migration with `pnpm exec wrangler d1 migrations apply DB --local --config examples/audit-export/wrangler.jsonc`. Run `pnpm example:audit-export` and invoke its local `/__scheduled` endpoint. For an isolated test instance set a different database/state directory. This example performs only read requests to Loginflare; writes go to the example's own archive.

For deployment, create a separate D1 database, set its ID, apply this example's migration with its config and store the machine secret as a Worker secret. Review the five-minute Cron before deploying/configuring it yourself. Never use Loginflare's database as the archive. `pnpm check` includes tests, generated bindings and a deployment dry run, which does not deploy.

Each invocation acquires a 60-second D1 lease, fetches the newest 100 records, then continues its previous older-page sweep. It commits archive inserts and the next signed cursor together, keyed by audit ID. At most five pages are processed, with a 20-second admission budget and bounded network requests. API/storage failures leave committed progress intact; expired leases recover interrupted exporters. A completed sweep restarts on a later invocation, catching records inserted while older pages were read. Invalid cursors after source key rotation restart the sweep; ID deduplication prevents repeat rows. Changing issuer or machine identity fails with `ARCHIVE_SOURCE_CHANGED`; intentionally use a new archive database for another source/identity instead of mixing cursor scopes.

The archive includes actor/target IDs, result/reason, request ID, IP, user agent and event time when supplied; unknown fields are discarded. It stores neither machine tokens/secrets nor raw API responses. Logs contain counts or a fixed failure code. Archive access, encryption/backup policy, personal-data retention and downstream export are the application's responsibility. This example retains archive records indefinitely; D1 storage is finite, so size it and implement a reviewed lifecycle for your needs.

This is an **at-least-once read-and-copy example**, not a source snapshot or an unlimited-throughput/lossless replication service. Audit source retention is 90 days. Without additional invocations, Cron reads at most 500 rows per five minutes, with overlap for head polling and repeat sweeps. You must complete sweeps before source expiration and monitor failures/backlog; outages or sustained load beyond the budget can lose records before they are read. Read-only polling cannot atomically acknowledge source deletion. The leased checkpoint records progress, not proof of a complete historical archive. Business webhook notifications remain a separate contract.
