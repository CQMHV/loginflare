# 业务事件通知

[English](webhooks.md)

管理员在 `/zh-cn/admin/webhooks` 配置 Webhook、查看投递记录。这些通知异步描述账号事实，与安全审计日志分开；本阶段不提供同步 Actions，也不开放机器端的 Webhook 管理权限。

## 配置接收端

1. 准备公开的 HTTPS 443 接收地址。[接收示例](../examples/webhook-receiver/README.zh-CN.md)演示验签和按事件 ID 写入持久化、去重的 inbox。
2. 创建停用状态的 Webhook，选择事件，保存仅显示一次的签名密钥，将其放入接收端 secret。配置列表不再返回密钥；Loginflare 使用实例认证密钥加密保存。
3. 接收端就绪后启用订阅。仅订阅之后产生的事实，不补发历史。最多启用 20 个订阅，总配置最多 100 个。
4. 在投递记录中按订阅 ID、事件 ID、状态筛选，查看结果代码和尝试记录。手动重投使用当前配置、保留同一事件 ID，接收端须幂等处理。

配置和投递时，地址必须仅解析到公网。拒绝私网、环回、保留地址、公私混合 DNS、非标准端口、URL 用户名密码和重定向。部署的 Worker 必须保留 `global_fetch_strictly_public`，由运行时进一步约束实际连接，防止解析后的地址变化。不要在地址查询参数中放凭据；管理员可读取配置 URL。

修改地址、事件类型、启停状态或签名密钥会推进配置代次，后台分批取消旧代次待投递任务；已发送的请求可能完成。仅重命名不取消任务。轮换时先停用、轮换密钥、更新接收端，再启用，按需要重投保留期内的事件。过期版本的重复轮换会被拒绝。仅可删除停用且没有保留投递记录的配置。

## v1 合同

```json
{
  "version": "v1",
  "id": "e5dd4b593f434fafb36a4f6d896d57b2",
  "type": "user.updated",
  "occurredAt": "2026-11-14T00:00:00.000Z",
  "subject": { "type": "user", "id": "account-id" },
  "data": { "fields": ["name", "locale"] }
}
```

| 类型 | data | 含义 |
| --- | --- | --- |
| `user.created` | `emailVerified: boolean` | 用户记录创建，包括已验证的社交账号开通。 |
| `email.verified` | `primary: boolean` | 初始已验证账号开通，或邮箱从未验证变为已验证；不含邮箱地址。 |
| `user.updated` | `fields: string[]` | `name`、`username`、`email`、`image`、`locale` 的实际变化，仅字段名，不含值。 |
| `user.suspended` | `{}` | 账号变为停用；不包含注销过程的冻结。 |
| `user.restored` | `{}` | 账号从停用变为正常。 |
| `user.deleted` | `{}` | 最终物理删除完成；事件和主体 ID 在账号删除后保留。 |

不发送密码、令牌、验证码、密钥、邮箱地址、资料值或完整认证 URL。主体 ID 仍属于个人数据，接收方应保护访问与保留策略。事件描述已提交的数据库事实，不等同于 HTTP 操作成功：同一事务回滚时不会留下事件；分别提交的写入及后续补偿写入可能各自产生事实。申请注销不表示最终删除完成。业务事件不是关联应用会话的单点退出协议。

请求为 JSON POST：

| 请求头 | 值 |
| --- | --- |
| `Loginflare-Event-Id` | 跨订阅和重投保持不变的事件 ID。 |
| `Loginflare-Delivery-Id` | 同一事件与订阅组合的稳定投递 ID。 |
| `Loginflare-Timestamp` | 本次发送的 Unix 秒数。 |
| `Loginflare-Signature` | `v1=` 加小写十六进制 HMAC-SHA256；签名输入为 `timestamp + "." + 原始请求体`，使用签名密钥。 |

解析、执行前使用密码库的恒定时间校验验证 MAC，拒绝超过五分钟时钟容差的时间戳，校验 v1 数据结构，并核对请求头与正文中的事件 ID。返回 2xx 前，将事件 ID 去重记录与业务写入一起持久化。时间窗口内的重复请求、重新签名的手动重投均不得重复业务效果。示例只写持久化 inbox，不执行外部副作用；后续消费者需要自己的重试与幂等策略。两端时钟应保持同步。

## 投递与恢复

SQLite 触发器让不可变事件、订阅任务与账号变更处于同一事务。事件不外键关联被删除的主体。成功的变更请求通过 `waitUntil` 尽快尝试投递，原有每五分钟 Cron 负责到期重试和中断恢复。登录响应不等待接收方。必须保留 Cron；恢复备份时一并恢复订阅配置、接收端 secret 和实例认证密钥。

D1 条件领取与 30 秒租约协调不同实例。单次后台调用最多发送三个任务，使用 20 秒启动预算；每个任务的 DNS、请求和响应读取共享五秒截止时间。响应最多 64 KiB，不保存正文，不跟随重定向，仅 2xx 成功。已确认失败后依次等待 5 分钟、30 分钟、2 小时、12 小时、24 小时，每个周期最多六次已结算尝试，Cron 调度可能带来额外延迟。进程中断或结果未确认的尝试在租约到期后记为结果不明，不消耗已结算重试次数。

提供**至少一次投递，不保证顺序**。接收端成功后，Loginflare 仍可能丢失状态写回；重试保留同一事件 ID。手动重投创建新周期，保留累计次数和历史，要求当前订阅启用且仍匹配事件。配置与周期操作均使用版本条件更新。成功、最终失败或取消七天后可清理，已完成尝试同样保留七天。待投递任务及其引用的事件持续保留直到结算；无引用事件七天后过期。清理按子表优先、持久化游标分批执行，可能额外需要数轮 Cron；早期未完成事件不会阻塞后续历史清理。

这是有明确预算的 D1 outbox，不能视作高吞吐外部队列。没有请求触发工作时，Cron 每五分钟最多发送三个任务，由新任务与重试共享。多订阅、大积压需要按实际负载测量和单独设计。通过后台检查待投递时间、尝试次数和失败记录，不把重试计划当作延迟 SLA。错误只保存有限结果代码与 HTTP 状态，不记录响应正文和原始异常。

`0027_business_events.sql` 新增表、索引与原生事实触发器，不回放已有用户。沿用受审查的迁移、备份恢复流程；主 Worker 不需要新 binding。接收端与[审计转存示例](../examples/audit-export/README.zh-CN.md)各自使用独立数据库，由操作者单独部署。审计转存通过现有 `management:audit:read` 复制安全和管理审计记录，不是 Webhook 订阅。

`pnpm test:events:recovery` 在被忽略的 `work/events-recovery` 下运行三个独立数据库的恢复演练：接收端成功、投递状态写回丢失后停止运行时，校验并复制快照，再从副本启动，核对重复抑制、未确认尝试恢复和审计续读。全部出站流量在本地模拟，报告只含计数和断言，不含凭据。
