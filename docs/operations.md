# Operations and recovery

[简体中文](operations.zh-CN.md)

`GET /api/health` reports Worker liveness without accessing D1 or R2. `GET /api/readiness` returns 200 only when the canonical installed instance can read D1 and its current private key material; failures return 503 with no configuration details. It bypasses the normal 30-second key-material cache. Poll readiness at a bounded interval (for example once a minute). It does not send email, call Turnstile or verify media delivery. An incomplete installation is not ready.

Workers Logs contains structured `http_request` events: production samples successful requests at 1% and records all 5xx responses. Use request IDs to investigate failures. These sampled logs cannot supply an exact authentication conversion rate. Authentication audit events distinguish incomplete MFA from completed sign-in. Expected 4xx authentication refusals are not service outages.

`durationMs` measures the Worker entry through response creation, including installation resolution and browser-account selection; it excludes background `waitUntil` delivery and response-body streaming. It is not browser TTFB or a database-only timing.

The required `REQUEST_LIMITER` Workers rate-limit binding admits up to 600 dynamic requests per minute per edge-provided source address (IPv6 grouped by /64), before installation, authentication or D1 reads. GET/HEAD requests for static assets and `/api/health` are exempt. Cloudflare's limiter is approximate and local to a location; it does not impose a global quota. Existing endpoint and account quotas remain in effect. A denied request returns 429 with `Retry-After`; a failed admission binding returns 503. Preserve this binding when updating environment-specific Wrangler configuration.

Every mail delivery path shares atomic D1 budgets: 3/minute and 20/day per normalized recipient, plus 300/minute and 10,000/day per instance. These are fixed windows starting with the first reserved attempt. Recipient keys contain SHA-256 digests rather than addresses. A reservation is charged before delivery, including uncertain provider failures; rejection does not replace an existing code. Anonymous verification and recovery requests retain opaque responses when delivery is suppressed, while authenticated code operations return 429 with `Retry-After`. Investigate quota exhaustion separately from delivery outages. These application quotas do not replace provider limits or an operator's spending controls.

Webhook delivery scans run after event-producing user mutations and explicit notification changes/retries, with scheduled delivery retained for recovery. Login-flow bookkeeping and unrelated successful writes do not start empty delivery scans.

For authentication 5xx responses, correlate `X-Request-ID` with `auth_request_failed.requestId`. Its allowlisted `reason` distinguishes `TURNSTILE_UNAVAILABLE`, `DATABASE_ERROR` and `AUTH_INTERNAL_ERROR`; raw upstream errors and SQL are not logged. Turnstile transport/HTTP failures return 503 with `TURNSTILE_UNAVAILABLE`, while rejected verification stays a 4xx. A removed passkey during MFA returns 400 with `PASSKEY_NOT_AVAILABLE`, including a deletion at the final session insert; restart sign-in with an available method.

Monitor readiness, 5xx rate and latency, `email_recovery_delivery_failed`, `database_maintenance_failed`, and deployment failure output. Other delivery errors follow the request failure path. Investigate repeated delivery failures without changing account-verification requirements. Inspect maintenance failures and oldest pending expiry work before increasing cleanup budgets. Never log request bodies, cookies, tokens, complete OAuth URLs or mail links.

For configured account Webhooks, also inspect `webhook_delivery_failed`, `webhook_maintenance` and the oldest pending/failed delivery records. Receiver failures do not block login. Preserve the instance authentication secret with encrypted subscription keys; keep the separate receiver's secret, inbox deduplication and archive/checkpoint backups consistent. Use the [isolated event recovery exercise](webhooks.md#delivery-and-recovery) after relevant changes. Audit export failures appear in its independent Worker as `audit_export_failed`; bounded polling must catch up before the 90-day source retention expires.

Before upgrading, identify the exact Worker, D1, media R2 and PRIVATE R2 bindings, issuer, migration ledger and pending migration hashes. Validate the previous Worker against any online migration before adding its digest to `migrations/online.json`; do not add approval merely because SQL executes. Preserve private installation material and its fingerprint.

For local recovery, stop all writers, create and verify a snapshot as described in [Scaling](scaling.md#schema-and-recovery-gate), and restore into isolated state. Check schema/foreign keys and media references, then verify password login, enabled TOTP, an existing session and a rotating refresh token before accepting the recovery.

For remote recovery, retain the original bindings and issuer, use D1's recovery facilities for the reviewed recovery point, and recover matching R2 data and private material. A database recovery point alone is not a consistent multi-storage backup. Do not run setup against existing restored data. A Worker rollback restores code only. This release does not offer a turnkey remote import/restore command or promise a recovery time or production throughput.
