# Architecture

[English README](../README.md) · [简体中文说明](../README.zh-CN.md)

Loginflare is a general account and identity platform for independent deployments from small teams to large public-facing services. It combines a user account center, an administrator console, and standard OAuth/OIDC integration. The maintainer's personal test instance does not restrict independent deployment uses. Other operators fork the repository and configure their own instances. Business-specific applications can build on the platform in separate branches with their own branding and rules.

## Runtime boundaries

```text
Browser: React 19 + Material Web + React Router + react-i18next
    |
    | same-origin HTTPS
    v
Cloudflare Worker
    +-- Workers Static Assets: browser application
    +-- Hono: routing, request boundaries, authorization, safe errors
         +-- R2: private avatar storage, public image responses and bounded lifecycle cleanup
         +-- Better Auth: email/password, username, sessions, admin, CAPTCHA, OAuth provider and JWT
              +-- D1: accounts, sessions, verification, rate limits, OAuth clients/tokens/consents, signing keys
              +-- Email Service binding: transactional delivery
              +-- Turnstile: server-side verification
```

The application has one Worker, one D1 database and one private R2 avatar bucket per environment. Local, staging, and production data, files and secrets are isolated. It does not require KV, Queues, Durable Objects, an external database, or an external email provider.

D1 is the only implemented database backend. Registered-account volume and concurrent request capacity are separate dimensions. Large public deployments must be measured against their own traffic mix and current platform limits; a million stored accounts is not a claim of a million concurrent users. Hyperdrive and external SQL backends are future integrations, not supported configurations. See [Scaling and validation](scaling.md).

Authentication instances are constructed with the current request's bindings. Request-scoped database objects must not be cached globally. Authentication schema changes use versioned SQL migrations rather than a second user model.

## Browser interface

The interface follows Material Design 3. React 19 renders the actual Web Components provided by the pinned `@material/web` 2.5.0 dependency. Shared MD3 design tokens control colors, typography, shapes, and interaction states across authentication forms, account pages, and administrator views. Layout and responsive styles remain in application CSS.

Account preferences, email addresses, and sessions use Material lists and list items, with Material dividers between records. Action links use Material text or icon buttons. Sidebar navigation keeps React Router links with Material ripple and focus-ring components, preserving current-page announcements, keyboard activation, and native link behavior. Cards, avatars, status labels, and tables use application markup because the pinned Material Web package has no corresponding components.

The account center (`/account/*`) and administrator console (`/admin/*`) mount separate layouts and navigation trees. Account navigation contains only personal profile, emails, security and sessions; administrator navigation contains only users and applications. An administrator can explicitly switch areas, and each area's brand link returns to its own home. The entire administrator layout requires the administrator guard, while API authorization remains enforced by the server. The localized `/admin` entry opens user management. Theme, language and sign-out controls share the visual shell without combining the two areas' navigation.

The header groups language and theme access into compact Material filled-tonal icon buttons and uses the account's circular avatar as its account-menu trigger. Translation and contrast symbols are bundled SVG assets from the pinned Material Symbols package, with no icon-font download. A configured profile image fills the avatar; an absent, invalid or failed image uses the same fixed Material person SVG placeholder across header, profile and user-table avatars. The placeholder scales with the avatar and retains an accessible label identifying its owner; display-name initials are not rendered. All avatars share Material Web's leading-avatar color mapping: `primary-container` for the fill and `on-primary-container` for the placeholder. These system roles resolve through the active light/dark theme; avatars do not define a separate fixed color or encode account status. The pinned package's `tokens/versions/v0_192/_md-comp-list.scss` defines this pairing. Native Material menus own their surfaces, positioning, motion and keyboard navigation; the avatar opens profile, administrator access when permitted, and sign-out actions. The same controls remain available on small screens. The account's language preference uses the default outlined select appearance, without custom corner or font-size overrides. Language changes preserve the URL query and fragment and retain the existing preference synchronization.

The profile page groups the photo, editable display name and username, join date and stable account ID inside one account-details card. The bundled Material pencil icon is always visible in a small lower-right button on the photo. The photo and edit control are sibling buttons with independent Material hover, press and focus feedback; pressing the pencil does not activate the photo's state layer. The edit control has a 48-pixel touch target and holds any processing indicator while the avatar stays visible. Clicking or keyboard-activating either control opens image selection and the existing crop/upload flow; there is no separate change-photo text button. A contextual remove action remains available when a photo is configured. Display preferences stay in their own card. Profile drafts and avatar cache invalidation retain the shared browser-data policies below.

The crop editor is loaded only after selecting a valid image. The pinned MIT-licensed `react-easy-crop` component handles dragging, wheel and pinch zoom and keyboard positioning inside a fixed circular frame. Material controls provide zoom, quarter-turn rotation, reset and save/cancel actions. The initial/minimum 100% zoom fills the crop frame exactly, rather than filling the larger editor stage and discarding extra image content. The image's short side meets the frame, and drag limits prevent the crop from extending beyond the source. Non-square sources necessarily lose part of their long side. Returning to minimum zoom recenters the image. The preview is bounded to 1,600 pixels on its longest side; final 256-pixel WebP output replays the displayed translation, rotation and scale from the decoded original. No full-resolution rotated canvas is allocated. The editor mounts after the Material dialog finishes opening, observes its available size and keeps the action footer outside its scrolling content. Its CSS is bundled locally with automatic style injection disabled; neither media nor styles are loaded from a third-party service.

Brand emphasis uses `--loginflare-brand` (`#F38020`) with dark `--loginflare-on-brand` labels. The MD3 primary role uses a deeper orange for readable links, field labels, and focus indicators. Filled-button label/icon tokens cover normal, hover, focus, and pressed states; destructive actions retain the semantic error palette.

The orange entrance and sign-in arrow and the outlined Loginflare wordmark are authored in `public/assets/logo.svg`. Page brands reference its `#logo` group, with lettering that inherits the active theme's text color. `public/favicon.svg` contains the matching symbol alone. Both assets use vector paths without embedded images or font dependencies.

`/assets/theme.js` is a same-origin, blocking head script that applies the initial theme before the client module loads, without inline script or a weaker CSP. It owns the browser-local `loginflare.theme` preference (`system`, `light`, or `dark`), observes system color-scheme changes and cross-tab storage events, and exposes a stable snapshot to React through `useSyncExternalStore`. Manual choices override the system until System is selected again. Dark mode replaces the MD3 color roles and browser `color-scheme`; the brand orange stays the same. Turnstile is recreated with the active theme, invalidating the previous client-side CAPTCHA token until the new widget completes. No account schema or authentication API changes are required.

Material Web and the Roboto/Noto Sans SC variable fonts are bundled into the client build; UI components and fonts are not loaded from an external CDN. The plain and brand typeface tokens share the same stack as ordinary page text: Roboto for supported scripts, Noto Sans SC for Chinese, then system fallbacks. The pinned Fontsource packages provide normal faces covering weights 100–900, including Material's 400/500/700 weights. Their `unicode-range` WOFF2 subsets load only for characters needed by the page. A shared Vite PostCSS policy sets `font-display: optional` in development and production without modifying installed font packages or duplicating their subset definitions. The common Roboto Latin file is preloaded with its build-resolved asset URL; Chinese subsets remain demand-loaded. When fonts miss the browser's brief initial window, the page keeps its fallback rather than replacing visible text after a slow download. Font availability may therefore differ on a slow first visit; avoiding a late visual change takes priority. Existing same-origin CSP rules allow these assets without broader font permissions. Material Web's Apache-2.0 license and the fonts' OFL-1.1 licenses are included in the generated third-party notices. The upstream component project is in [maintenance mode](https://github.com/material-components/material-web/discussions/5642); dependency versions are explicitly pinned.

## Browser data and navigation

TanStack Query owns browser server-state fetching, sharing, cancellation, freshness and inactive-result collection. A single client lives in each document's memory. Native authentication mutations and OAuth SDK requests retain their protocol behavior; there is no blanket HTTP cache or global fetch override. Account and administration pages use these policies:

| Resource | Freshness | Invalidation |
| --- | --- | --- |
| Current identity/profile | 15 seconds, bounded by session expiry | Document reload, stale visibility/reconnect events, profile changes |
| Email registry | 60 seconds | Add/remove/verification/primary changes; primary changes also update identity and user views |
| Personal session pages | 15 seconds | Revocation and password changes invalidate cached session pages |
| User/application lists and details | 60 seconds | Related mutations invalidate details and all list/filter/cursor variants |
| Public CAPTCHA configuration | 5 minutes | Shared between widgets; fetched when needed after expiry |
| Signed OAuth consent context | No reusable freshness or inactive retention | Bound to actor and signed request; no focus/reconnect refresh or automatic retry |

Expiry makes data eligible for revalidation; it does not start polling or erase results. Fresh results are reused across route and language changes. The profile page observes the shared identity query so returning to it revalidates an expired result without duplicating a fresh read. Stale results stay visible during background refresh, which is announced to assistive technology without adding a toolbar or moving page content. Initial reads show loading feedback; failures show an error, retained-data notice where applicable, and a retry action. There is no persistent refresh button; a document reload fetches current data. Only network/5xx query failures retry once. Automatic mount/focus/reconnect reattempts have an error cooldown and honor `Retry-After`; other 4xx errors and writes do not automatically retry. Hidden pages defer cross-tab-triggered reads until visible. BFCache restoration rechecks identity and then active private data.

Private keys include account ID, session ID, role, resource and full query parameters. Identity-boundary changes cancel and remove obsolete queries. Private unauthorized/banned responses end cached identity; forbidden responses refresh authoritative identity. Known session expiry clears private data. Server authorization and immediate credential revocation remain authoritative on every API request, independently of display freshness. Private results and draft caches are never persisted to browser storage.

Inactive queries are collected after five minutes, with at most 50 settled inactive private results retained. Account/role-scoped ordinary drafts and scroll positions have separate memory stores bounded to 30 and 50 entries. Scroll restoration stays active through the initial rendering frames to accommodate asynchronous Material component layout, and user input ends restoration immediately. Submitted filters/cursors remain in URLs. Profile/application edits and unfinished searches survive SPA navigation; pristine fields follow refreshed data, while unsaved edits survive background reads and late save responses. Drafts can be discarded. Same-account session rotation clears obsolete queries and sensitive inputs while retaining ordinary page state and security-action acknowledgements.

F5 creates a new client, revalidates identity/current-page data, and restores URL state. Passwords, codes, recovery/verification workflows and newly generated client secrets stay component-local and clear on route departure or `pagehide`; delayed mutation results cannot restore secrets after that boundary. Sign-out/account/role changes reset private page state. `BroadcastChannel` exchanges only event names, resource groups and an account ID; other tabs refresh or clear their own state without transferring query contents or credentials. Language/theme persistence remains independent.

Browser regression tests cover resource reuse, filter/cursor separation, cache bounds, F5/error retry, visibility/reconnect/BFCache signals, stable layout during background reads, stale failures, draft/scroll restoration, mutation invalidation, cross-tab changes, permission loss and late responses after account changes. Fixtures remain local. This frontend policy adds no Worker bypass, binding or schema migration.

## Avatars

Better Auth's native `user.image` remains the authoritative profile URL. `POST /api/account/avatar` accepts a cropped raster upload and `DELETE /api/account/avatar` removes the current image. Both require an eligible cookie session and the exact account Origin; clients cannot supply an owner or arbitrary image URL through the native signup/update routes. Uploads have atomic account/IP limits, and the final D1 write rechecks the current session, expiry, verification and suspension state after R2 completes.

The browser accepts static JPG, PNG and WebP sources up to 20 MiB, 16384 pixels per side and 100 megapixels. It checks file size and container dimensions before decoding; decoding and cropping use the user's device, and the decoded bitmap is closed when selection is replaced or discarded. Its Canvas crop produces a 256-by-256 WebP image at an encoder quality of 0.86. The output MIME is checked before upload: browsers that cannot encode WebP show an explicit error, and encoding failures preserve the existing photo. There is no PNG/JPEG upload fallback. The Worker accepts only WebP at that exact size, at most 300 KiB, checks the actual bytes against `image/webp`, rejects animation, and strips EXIF/XMP/ICC metadata. This is bounded container validation, not a second image-decoding service. Original files, filenames, crop drafts and image pixels are not stored in D1 or browser persistent storage. Photo selection is discarded on page departure.

R2 is private. The Worker exposes an opaque, immutable file address at `/avatars/:id` for profile images and OIDC `picture`. Anyone with that address can read it; no account cookies or D1 lookup are required. Public image responses have a five-minute browser cache, ETag/conditional GET/HEAD, a cross-origin resource policy for embedding in applications, and an image-only restrictive CSP. Replacements receive a new address. Removing a photo clears the profile reference. Old addresses remain readable until bounded maintenance removes their objects, and cached responses can outlive that removal by up to five minutes. No external image proxy or email-based avatar lookup is used.

`userAvatar` stores file lifecycle metadata, not another user record. A pending row is inserted before R2 writes, with a one-hour expiry. Updating the native image and retiring the previous row happen atomically through D1 triggers, including concurrent replacements. Failed/uncertain uploads remain collectable; a successful native reference keeps its object. Scheduled maintenance seeks expired asset candidates using `(deleteAfter, id)`, removes at most 500 candidates per batch, checks owner references before R2 deletion, and shares the existing twenty-batch/twenty-second budget and five-minute safety buffer. It never enumerates the bucket or counts all users. R2 deletion failures leave rows/cursors for a later run. Deployment capacity and R2 operation/storage costs still require measurement for the intended traffic.

## HTTP surface

Page paths are localized under `/en-us/` and `/zh-cn/`. Language identifiers inside the program remain `en-US` and `zh-CN`. Explicit URL language takes precedence over saved preferences. At the root, a shared client resolver chooses the saved browser preference, then the signed-in account locale, then the first supported browser language, with English as the final fallback. English and Chinese regional/script variants use the available `en-US` and `zh-CN` translations. Both initial i18next/HTML language and React routing use this resolver. Root and localized entry navigation replaces browser history, preserves raw query/fragment values, and selects account or sign-in according to session state. Browser detection does not change the stored account/email locale; only the existing explicit preference updates do.

API routes are not localized. `/api/auth/*` reaches the selected Better Auth endpoints through Hono's route/method boundary. `/api/health` only reports service health. Unknown API routes return JSON errors, never the SPA HTML entrypoint.

Only required user and administrator operations are exposed. The presence of a Better Auth plugin does not expose all of its operations. Role assignment, account deletion, administrator-set passwords, and impersonation are excluded from the public HTTP surface. Email management and code-based recovery use the Loginflare email plugin; the generic native change-email and request-password-reset routes are not exposed.

External applications use the dedicated OAuth/OIDC surface. The issuer is `${AUTH_URL}/api/auth`; protocol requests use their native methods and content types. Registered SPA callback Origins receive protocol-only CORS access without account cookies. Account and administrator APIs remain same-origin JSON. Discovery and JWKS are public, while the JWT plugin's standalone `/token` route, dynamic registration, native/device grants, and client credentials remain closed.

Application management is exposed through `/api/admin/applications` with server-side administrator checks. Creation, detail, editing, disabling, and secret rotation use the provider's management APIs; the list uses a bounded D1 projection containing only client ID, name, type, disabled state, and creation time. General client self-registration remains closed. Clients share an instance reference and are managed by all instance administrators. Redirects use the upstream web-client policy: exact HTTPS URLs on non-loopback hostnames. The local examples satisfy that policy with HTTPS `web.localhost` and `spa.localhost` hostnames.

The list surface is `GET /api/admin/users`, `GET /api/admin/applications`, and `GET /api/account/sessions`. The native `/api/auth/admin/list-users` and `/api/auth/list-sessions` routes are not exposed. Lists use `(createdAt, id)` keys, or `(createdAt, clientId)` for applications, with descending indexed ordering and a bounded `limit + 1` read. A signed cursor binds its direction and position to the entity, owner, and exact lookup. User search supports ID, username, or primary email; application search supports client ID or full name. No arbitrary sort, offset, substring filter, or exact-total query is exposed. Responses contain `items` and `pageInfo` with next/previous cursors. Session pages also report `hasOtherSessions` independently of the page length. Native session-revocation operations remain in use.

The browser stores cursor and exact lookup parameters in the URL, restores them after detail navigation, and shows only the current page's size. Previous, Next, and Return to latest replace numbered pages and a total count.

OAuth callback Origins and exact post-logout destinations have an indexed `oauthClientUri` projection maintained by triggers. Callback strings remain authoritative in the native client fields. Migration preparation derives Origins with the URL parser into `metadata.loginflareRedirectOrigins`; protocol checks seek this index rather than enumerating every application. Creation and updates keep the metadata and indexed projection synchronized.

## Identity and authorization

`user` and `admin` share one account system. Public signup produces ordinary users. Email verification is required before sign-in. Administrator provisioning is an operator action against a specified existing verified account; it is not triggered by signup order or a public setup route.

The official Username plugin adds a unique, lowercase `username` to the existing user model, without a separate `displayUsername` field. Display names remain independent and need not be unique. The browser's sign-in field accepts an email address or username and selects the corresponding native password endpoint; both endpoints use Turnstile, persistent rate limiting, email-verification checks, and account-suspension rules. Username sign-in also preserves the provider-signed OAuth query. Usernames contain 3–30 ASCII letters, digits, underscores, or dots and match case-insensitively. The nullable field preserves existing accounts without inventing login names; those users can choose or change a username in their profile. Configuring username support does not change the account's stable user ID or OIDC subject.

The dedicated localized `/account/emails` page manages all addresses. Better Auth's `user.email` and `emailVerified` remain the authoritative primary email and its verification status. An email registry records primary and secondary addresses with global case-insensitive uniqueness, covering both registration and subsequent management. Verified secondary addresses can become primary; the previous primary remains registered as secondary. Only the primary address or username identifies a password sign-in, and the stable user ID, credentials and OIDC subject do not change when the primary address changes.

Email management requires a valid unbanned session, same-origin JSON, and current-password confirmation for sensitive changes. Adding an address proves mailbox access with a short-lived code. Recovery first resolves a username or primary email, then sends a code only to a specified verified address registered to that account. Unknown accounts and ineligible destinations return a generic challenge result. Codes bind the account, address, purpose and individual challenge, are stored as hashes, and have bounded attempts, lifetime and send rates. A verified recovery challenge produces a native Better Auth reset token; native reset owns password hashing, single-use consumption and security-event revocation. No secondary email can independently select an account.

The console can inspect ordinary users, suspend/restore them, and revoke their sessions. Administrator accounts cannot be suspended through this console. Browser navigation checks improve the experience; server checks enforce permissions.

Sessions are stored and checked in D1, without a cached cookie user snapshot or read replicas. Suspension revokes sessions, and restoring an account does not restore them. Password change revokes other sessions; password recovery revokes all sessions. No browser persistent storage contains authentication tokens.

The OAuth provider and core are pinned together at 1.7.13. Authorization code + PKCE S256 is required for both Web and SPA clients. The provider owns code consumption, token rotation, client secrets, consent, and protocol validation; its JWT plugin issues RS256 ID Tokens and encrypts private signing keys stored in D1. Access tokens are opaque because no business resource audiences are registered. Roles and administrator capabilities are not issued as application permissions.

Ordinary logout preserves the provider's `offline_access` refresh-token semantics. Security events have a separate Loginflare revocation policy. The [integration guide](oauth.md) describes the resulting behavior and the limits of application-owned sessions. There is no global logout notification service or custom OAuth protocol implementation.

## Multi-factor authentication

Better Auth's two-factor plugin owns TOTP enrollment, encrypted secrets and recovery codes, signed ten-minute login challenges, single-use challenge/code consumption, per-challenge attempt budgets and account lockouts. MFA is optional per account and protects both password endpoints. The plugin runs before the OAuth provider's completion hook, so signed OAuth state continues only after a successful second factor. The localized `/two-factor` page accepts authenticator codes or recovery codes; verification endpoints also accept the provider-signed `oauth_query`.

The security page requires the current password for enrollment, recovery-code regeneration and disabling. Enrollment stays inactive until a TOTP is verified. QR codes render locally, and setup secrets/codes stay in component memory; page hiding, session rotation and account changes clear them. Users must acknowledge saving their codes before confirming enrollment. The gateway exposes only enable, disable, verify-TOTP, verify-backup-code and generate-backup-codes, with same-origin JSON and field allowlists. OTP delivery, trusted devices and backup-code viewing are not exposed.

Enrollment confirmation and disabling rotate the current session and revoke other sessions plus prior OAuth grants. Password reset preserves MFA and invalidates pending MFA challenges. Verification rechecks account eligibility when creating a session, including accounts suspended after the password step. Native D1 rate limiting applies to all two-factor endpoints; account lockouts also bound failures across source addresses. Migration `0011_mfa.sql` adds the plugin schema and an index for revoking challenges by user. No new Worker bindings or secrets are required; keep `BETTER_AUTH_SECRET` stable because it encrypts the stored credentials.

## Mail and failure behavior

Email Service sends registration-verification links and email-management/recovery codes using both HTML and plain text in the account's preferred language. Registration token values must survive URL handling unchanged. Private verification delivery failures provide a retry/resend path. Public recovery delivery runs through the request's `waitUntil` callback and returns the same generic result on failed delivery, so delivery status and network latency do not disclose account eligibility. Failed delivery invalidates its challenge and records only a redacted failure event. There is no automatic provider switch or verification bypass.

Local email delivery is simulated. Production configuration must include the verified sending domain and required email binding. Logs must omit secrets, passwords, session tokens, and full recovery or verification URLs.

Structured API request logs include a generated request ID, method, known route, status, and duration. Development logs requests; remote environments retain server errors and a small sample of ordinary requests. Reset-link path tokens are replaced with `:token`; request queries, bodies, cookies, OAuth codes, client secrets, and tokens are never logged. Automatic platform invocation logs and traces are disabled, and query-string redaction is enabled.

Turnstile and persistent rate limits protect sensitive authentication endpoints. Missing/invalid challenges and verification service failures reject the request. Production must never use Turnstile test credentials.

## Data integrity and maintenance

Native Better Auth date columns use ISO UTC text consistently for comparison, ordering, and API serialization. Custom code-challenge and rate-limit clocks use explicit integer milliseconds. The migration wrapper prepares existing native dates and OAuth callback metadata before applying SQL migrations, then verifies the committed tables, columns, indexes, triggers, foreign keys, date storage, and callback/URI-registry consistency. Origin updates compare the old callback strings and metadata and stop on a conflict. Operators pause application registration, callback editing, and related writes until migration and the new Worker switch complete; the wrapper does not establish this window automatically. `pnpm db:check` checks local state without repairing it; remote checks require an explicit environment. Runtime schema autodiscovery remains disabled because deployment owns the schema gate.

Rate-limit consumption is an atomic conditional D1 UPSERT, so concurrent requests cannot each pass a separate read and overwrite the count. The custom request boundary preserves endpoint-specific windows, CAPTCHA, and native authentication behavior; denied requests do not extend the counter window. Limits fail closed if storage is unavailable.

A five-minute Cron Trigger invokes expiry maintenance on the existing Worker. Each run has bounded batches and time, uses expiry indexes, and retains a safety buffer. It collects expired rate counters, email challenges, verification records, credentials, and eligible grant-policy records. References are checked before deleting sessions or refresh tokens so cleanup cannot change offline authorization semantics through foreign-key cascades. Grant policy outlives every credential that could still use it. Records remain invalid when expired even if cleanup has not run; cleanup is separate from authentication validity and request latency.

Backups include SQLite snapshots for local D1 and R2 metadata, R2 blob files, and the local configuration/credentials needed to reopen the instance. Stop avatar writes before a combined file/database backup or restore. Database state, avatar files, issuer, and authentication secret form one recovery unit, including encrypted signing keys. Remote updates use D1 recovery mechanisms and a separately retained copy of the R2 objects against the reviewed environment. A Worker rollback alone does not restore database contents or uploaded files.

## Validation boundaries

Vitest and Workers integration tests exercise the Worker with local data. Playwright exercises localized user and administrator journeys and independent standard-client examples in a real browser. Example TLS certificates are local files, browser certificate exceptions and host-resolution overrides apply only to the test process, and system certificate/DNS settings remain unchanged. Local mail simulation and Turnstile test behavior are used instead of production resources. Remote deployment, real delivery, and resource provisioning are separate operator actions.
