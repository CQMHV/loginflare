# Third-party sign-in

[简体中文](social.zh-CN.md) · [Deployment](deployment.md) · [Application integration](oauth.md)

Administrators configure Google, GitHub, Microsoft, Discord, X, Telegram, OpenID Connect and OAuth 2.0 connections under **Administration → Third-party sign-in**. Multiple connections of each type are supported. Applications continue to integrate with Loginflare's issuer and OAuth/OIDC endpoints; they never need the upstream client credentials. Upstream access/refresh/ID tokens are used only during authentication and are not stored for API access or logout.

## Configure a connection

1. Create a connection with a display name, client ID and client secret. New connections are disabled. Copy its callback URL, `${AUTH_URL}/api/auth/callback/<connection-id>`, into the upstream client's exact redirect allowlist.
2. For Google, create a Web application OAuth client and configure its consent screen and test users as required by Google. For GitHub, create an OAuth App and set its authorization callback. For Microsoft, register a Web redirect URI in an Entra app registration and use its application (client) ID and client secret value. The tenant defaults to `common` (work/school and personal accounts); `organizations`, `consumers` and a specific tenant UUID are also supported and must match the app's supported account types. For Discord, create a Developer Portal application and register its OAuth2 Redirects. Presets reuse Better Auth's provider implementations and fixed endpoints. Microsoft requests only `openid profile email` by default, and Discord requests `identify email`. Every preset uses state and PKCE; Microsoft also verifies signature, issuer/tenant, audience and nonce.
3. For OIDC, enter the exact issuer, discovery URL, scopes and client authentication method. The discovery issuer must match; authorization, token, UserInfo and JWKS URLs must be public HTTPS services. The connector verifies signature, issuer, audience, expiry and nonce. `openid` is always included.
4. For OAuth 2.0, enter the authorization, token and protected user profile endpoints, scopes and client authentication method. Map the stable subject, name, email, verified-email boolean and avatar URL using dotted JSON field names, for example `data.id`. Empty optional mappings omit that field. Scripts and expressions are not supported. Use a provider-assigned immutable subject; do not map email or nickname as the subject. OAuth identities come from the protected profile response, never an unverified ID Token.
5. Save, use **Test sign-in**, inspect the returned profile, then enable the connection. Testing authenticates the current administrator with the upstream only; it creates neither users nor bindings. Drag the handles in the connection list to reorder login buttons; dropping saves the order. Touch and keyboard controls are also supported. Save edits before testing them.

For **X**, configure a confidential Web App with OAuth 2.0 in the developer console, then register the connection's exact callback URL and copy its OAuth 2.0 client ID and secret. The preset uses `users.read tweet.read`, state and S256 PKCE, and reads the stable user ID from the protected profile endpoint. It does not request offline access or write permissions. See [X's OAuth 2.0 setup guide](https://docs.x.com/fundamentals/authentication/oauth-2-0/authorization-code).

For **Telegram**, open the bot's **Login Widget** settings in BotFather, register the connection's callback under **Allowed URLs**, and use the displayed Login client ID and client secret. These are not the Bot API token. The preset uses Telegram's standard OIDC code flow with `openid profile`, state, S256 PKCE and nonce. It verifies the ID Token's signature, issuer, audience and expiry before reading the stable `sub`; no separate UserInfo request is made. Phone access and bot messaging permissions are not requested. See [Telegram Login](https://core.telegram.org/bots/telegram-login).

Secrets are encrypted in D1 with `BETTER_AUTH_SECRET`. Management responses expose only whether a secret exists. Leave the secret blank while editing to keep it, or enter a replacement. Preserve the deployment secret in backups; changing it without migrating encrypted values breaks connection credentials and pending flows.

The connection ID is permanent and never reused. After the first identity is linked, its type, client ID, Microsoft tenant, identity source/endpoints and subject mapping remain locked, including after unlinking. Create a new connection to replace an identity source. Secrets, labels, scopes and order can still change. Saving authentication configuration, disabling or archiving invalidates unfinished flows for the old revision; reordering alone does not change configuration revisions or interrupt authentication. Archiving is permanent. Disabling/archiving removes login buttons and prevents new sign-ins without revoking existing Loginflare sessions.

## Connection icons

Google, GitHub, Microsoft, Discord, X and Telegram presets include their brand icons without an upload, including for existing connections. The default follows the selected provider type; OIDC and OAuth 2.0 use a generic symbol. Custom icons take precedence and remain when switching provider type. Removing a custom icon or failing to load it falls back to the current provider's default. These defaults are bundled locally.

The connection editor accepts PNG, JPEG, WebP and SVG icons through the shared image picker. It uses the same file limits as avatars and brand logos: raster source files may be up to 20 MiB, 16384 pixels per side and 100 megapixels; SVG source files and all processed uploads may be up to 256 KiB. Preview and crop the icon, then save the connection to publish it. Raster images are encoded as square 256-pixel WebP files; SVGs pass the existing checks and retain their vector output. Login and registration buttons, account bindings and reauthentication choices use the same icon rules.

Icons are served from Loginflare's own origin and stored in the existing R2 bucket. Configuration accepts an uploaded `iconId`, never an arbitrary image URL. Unsaved uploads and replaced icons enter the bounded cleanup lifecycle after a one-hour grace period. Shared icons remain while any connection references them. Changing an icon does not change a linked identity's source or subject.

## Registration and account linking

An identity is `(connection ID, stable subject)`. Changes to upstream email or name do not change its owner. A trusted verified email permits immediate passwordless registration without a username. Otherwise the browser must complete local email verification first; no user, placeholder email or login session is created before that verification. Microsoft's ordinary `email` claim alone is not treated as verified. Discord's `verified` field must be `true`; otherwise local email completion is required. X and Telegram sign-ups require local email completion; X's account-verification badge and Telegram's phone verification are not email verification. Existing primary and secondary emails are reserved across all accounts. A conflict never merges accounts: sign in to the original account and explicitly link the third-party identity from **Account → Security**.

Linking may use a third-party account with a different email. It does not change or add Loginflare email addresses. Binding and unlinking require identity confirmation and remain bound to the initiating user/session. Unlinking atomically retains at least one usable sign-in method; disabled or archived connections do not count. Unlinking leaves profile data intact.

Accounts with a password confirm it for sensitive operations. Passwordless accounts reauthenticate an already linked identity, and complete Loginflare MFA when enabled. The server issues a five-minute, one-use confirmation bound to the user, current session and operation. This applies to linking/unlinking, email changes, first password setup and MFA management. Email recovery can set the first password, keeps MFA enabled and revokes old sessions, application grants and pending authentication proofs. If no linked provider remains available, use recovery through a verified account email.

Third-party sign-in cannot bypass Loginflare MFA. No usable new session or downstream authorization code is delivered before its authenticator/recovery-code challenge succeeds. Language, purpose and signed application authorization context survive callback, email completion and MFA. The existing OAuth Provider resumes authorization after completion; downstream `sub` remains the Loginflare user ID.

Each successful login fills only an empty nickname/photo. Existing values, primary email and username are retained. A missing nickname remains unset; displays may fall back to email. Avatar import downloads only the authenticated profile's URL through a protected same-origin endpoint. It uses the existing image checks, centered square crop, 256-pixel WebP encoding and private R2 lifecycle; the final update requires the avatar still to be empty. Import failure does not block login and a later login retries, including after a photo was deleted.

## Operational and API notes

- Public discovery: `GET /api/social/providers` returns enabled connection names, types, icon URLs and ordering only.
- Connection icons: `POST /api/admin/social-connections/icon` uploads an image and returns `iconId` and `iconUrl`. The shared 256 KiB upload ceiling also applies to avatar and brand-logo uploads; exceeding it returns HTTP 413 with `IMAGE_UPLOAD_TOO_LARGE`. Static raster icon uploads remain limited to 2048 pixels per side. Save the nullable `iconId` with the connection; `GET/HEAD /social/icons/:id` serves the validated image.
- Administration: `GET/POST /api/admin/social-connections`, `PATCH /api/admin/social-connections/:id`, `POST /api/admin/social-connections/:id/test` with a locale. Updates require the current revision; archived records remain visible. Create/edit requests do not accept `position`. `POST /api/admin/social-connections/reorder` atomically saves complete `{ order, previousOrder }` ID lists and reports conflicts when another administrator has changed the list.
- Restricted authentication: `/api/auth/social/start`, `/social/flow`, `/social/email`, `/social/verify-email`, `/social/finish`. Start accepts only a connection ID, locale, purpose and validated continuation/security context. Administrator testing uses `purpose: test`; callbacks use `/api/auth/callback/:id`.
- Account capabilities and identities: `GET /api/auth/social/security`; sensitive writes use `/social/unlink`, `/social/set-password` and existing email/MFA endpoints. Callers cannot override upstream endpoints, scopes or redirects.
- Generic upstream requests validate public HTTPS URLs, DNS addresses and same-origin GET redirects, with time/byte limits. Private, loopback, metadata and reserved destinations are refused. Connection failures do not initialize or affect local password sign-in.
- Migration `0012_social_connections.sql` adds encrypted ten-minute, browser-bound single-use flow state, five-minute operation proofs, identity uniqueness and immutable-source guards. Existing scheduled maintenance removes expired state in bounded batches. Existing users and application issuers are unchanged.
- Migration `0013_social_icons.sql` adds connection icon references and their R2 cleanup metadata. Apply it before running the icon-enabled build; it uses the existing D1 and R2 bindings.

- Migration `0014_social_provider_presets.sql` adds Microsoft/Discord types and immutable Microsoft tenants while preserving existing connections, icons, identities and pending state.
- Migration `0015_social_x_telegram.sql` adds X/Telegram types while preserving existing connections, bindings, icon references and unfinished authentication state.

Automated tests use isolated simulated upstreams and never operate real third-party accounts. Operators must supply configured client credentials for actual platform acceptance. SAML, organization SSO, WeChat/QQ-specific flows, upstream API authorization/token hosting and coordinated upstream logout are outside this release.
